## Key Design Decisions (viva-defensible)

| Decision | Reason |
|----------|--------|
| Scheduler is policy-only | Never executes — only decides order. Mirrors OS design |
| Executor is mechanism-only | Never decides order — only runs |
| Dispatcher bridges both | Makes scheduling delay independently measurable |
| `id(job)` in heap tuple | Prevents TypeError when priority+created_at tie |
| `threading.Condition` in PriorityScheduler | Proper blocking instead of spin-wait |
| Top-level `_worker()` in process_pool | Must be picklable for Windows spawn |
| `ml_simple` lazy import in registry | Prevents model training in every worker process |
| `asyncio.Future` + `call_soon_threadsafe` | Correct cross-thread→event-loop bridge |
| Delta-based psutil metrics | Measures what your code consumed, not process totals |
| JSONL logging | Append-safe, streamable, no schema lock-in |

## Viva Preparation

The five questions most likely to be asked:

**Q: Why is process executor faster than thread for CPU?**
A: Python's GIL prevents threads from executing CPU bytecode in parallel. Separate processes have separate GILs — genuine parallelism. Our data shows 43.6% reduction in execution time.

**Q: Why is async fastest for IO throughput?**
A: The event loop suspends coroutines at `await` points and immediately runs another. No thread blocking, no OS context switch. This is cooperative multitasking — many IO waits overlap.

**Q: Why does Priority scheduling hurt IO jobs?**
A: IO jobs have priority=3 (low). CPU jobs have priority=1 (high). Under high load, CPU jobs continuously arrive and jump the queue. IO jobs starve — we measured +80–212% waiting time at 100 users.

**Q: What is a voluntary context switch?**
A: When a process/thread willingly yields the CPU — e.g., when waiting for IO, sleeping, or waiting on a lock. IO workloads produce many voluntary switches because they frequently wait.

**Q: Why is baseline variance so high?**
A: Sequential execution exposes every job directly to OS scheduling noise. There is no buffering. Thread/process pools absorb request bursts. Our data shows CV=67.9% for baseline vs 38.9% for process.
