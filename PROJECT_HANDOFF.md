## What This Project Does

An HTTP server that accepts job requests, schedules them using FIFO or Priority policy, executes them via thread/process/async executors, collects OS-level metrics (CPU time, context switches, memory), and logs everything to JSONL for analysis.

The goal is to measure and compare how different OS scheduling policies and execution mechanisms behave under mixed workloads — and produce a viva-defensible academic analysis.

## File-by-File Documentation

### `src/core/job.py`

Central abstraction. Every HTTP request becomes a Job object.

```python
@dataclass
class Job:
    workload_type: str          # maps to registry key e.g. "cpu_fibonacci"
    params: Dict[str, Any]      # workload parameters e.g. {"n": 32}
    priority: int = 2           # 1=high, 2=medium, 3=low
    job_id: str                 # 8-char UUID fragment
    created_at: float           # timestamp at Job() creation
    enqueued_at: float          # set by scheduler.put()
    dequeued_at: float          # set by scheduler.get()
    started_at: float           # set by dispatcher._loop()
    completed_at: float         # set by executor callback
    waiting_time: float         # dequeued_at - enqueued_at (auto-computed)
    execution_time: float       # completed_at - started_at (auto-computed)
    total_time: float           # completed_at - created_at (auto-computed)
    os_metrics: Dict            # populated by executor after workload completes
    on_complete: Callable       # callback fired at end of mark_completed()
```

**Key design:** `on_complete` callback is how the server layer gets notified when an async executor finishes a job. The server sets this before submitting to dispatcher, and waits on a threading.Event or asyncio.Future.

**Important:** `on_complete` is NOT picklable. ProcessPoolExecutor passes only `(workload_type, params)` to worker processes — never the Job object itself.

### `src/core/registry.py`

Single dispatch table mapping `workload_type` strings to function calls.

**Why it exists:** All three executors need to call workloads by name. Having one top-level function (`run_workload`) makes it picklable for ProcessPoolExecutor.

**Critical:** `ml_simple` is imported lazily (inside the `ml_predict` branch only). If imported at module level, model training runs in every worker process on startup.

```python
def run_workload(workload_type: str, params: dict):
    if workload_type == "cpu_fibonacci":
        return fibonacci(params["n"])
    elif workload_type == "ml_predict":
        from src.workloads.ml_simple import predict_batch  # lazy
        return predict_batch(params["n_samples"])
    # ... etc
```

**Async workload types** (`io_file_async`, `io_sleep_async`) are NOT routed through `run_workload`. They are handled directly in `async_executor.py` via `_run_async_workload()`.

### `src/scheduler/fifo.py`

Thread-safe FIFO using `queue.Queue`.

- `put(job)` — calls `job.mark_enqueued()` then enqueues
- `get(timeout)` — blocks up to `timeout` seconds, calls `job.mark_dequeued()`, returns job or None
- `stats()` — returns enqueued/dequeued counts and current depth

No design issues. `queue.Queue` handles all thread safety internally.

---

### `src/scheduler/priority.py`

Heap-based priority scheduler. Lower integer = higher priority (1=high, 3=low).

**Heap key:** `(priority, created_at, id(job), job)`

**Why `id(job)` is required:** If two jobs have identical `priority` AND `created_at`, Python falls through to comparing the Job objects. Job has no `__lt__`. Without `id(job)` as tiebreaker, this raises `TypeError` and crashes. `id(job)` is unique per object in CPython.

**Blocking:** Uses `threading.Condition` wrapping the lock so `get(timeout)` properly blocks instead of spinning. This matches FIFOScheduler's blocking behaviour and prevents dispatcher busy-wait.

---

### `src/dispatch/dispatcher.py`

The bridge between scheduling policy and execution mechanism.

**Responsibilities:**
1. `submit(job)` — calls `scheduler.put(job)` (called by server layer)
2. `start()` — spawns background thread running `_loop()`
3. `_loop()` — continuously calls `scheduler.get(timeout=0.1)`, then `job.mark_started()`, then `executor_fn(job)`

**Important timing note:** `mark_started()` is called before `executor_fn(job)`. Since all executors are non-blocking (they return immediately after submitting to their pool), `execution_time = completed_at - started_at` includes thread/process pool queue wait time if all workers are busy. This is documented as a known measurement imprecision.

---

### `src/executors/thread_pool.py`

Wraps `concurrent.futures.ThreadPoolExecutor`.

- `execute(job)` — submits `_run(job)` to pool, attaches `_on_done` callback via `future.add_done_callback()`
- `_run(job)` — runs inside worker thread: calls `track_request()` + `run_workload()`
- `_on_done(future, job)` — called when future completes: calls `job.mark_completed()` which fires `on_complete`

**GIL note:** CPU-bound workloads do not run in true parallel here. All threads share one GIL. Only IO-bound workloads benefit from thread concurrency (GIL released during IO waits).

---

### `src/executors/process_pool.py`

Wraps `concurrent.futures.ProcessPoolExecutor`.

**Key constraint:** Only picklable data can cross the process boundary. Solution: `_worker(workload_type, params)` is a top-level module function (picklable). It runs `run_workload()` inside the child process, collects its own psutil metrics, and returns `(result, metrics)` tuple back to parent.

**Windows spawn guard:** On Windows, `ProcessPoolExecutor` uses `spawn` (not `fork`). The module is re-imported in each worker process. If the executor is created at module level (outside `if __name__ == '__main__':`), worker processes recursively spawn more workers → crash. The Flask server correctly guards this.

**Default max_workers=2** — process creation is expensive. Overcommitting on a laptop causes more harm than help.

---

### `src/executors/async_executor.py`

Runs an asyncio event loop in a dedicated background thread.

- `execute(job)` — calls `asyncio.run_coroutine_threadsafe(self._run(job), self._loop)` — thread-safe submission from dispatcher thread
- `_run(job)` — coroutine: if async workload → `await _run_async_workload()`; else → `await loop.run_in_executor(None, run_workload, ...)` to offload sync work
- Event loop runs forever in daemon thread until `shutdown()` calls `loop.stop()`

**Known limitation:** `track_request()` (psutil) runs in the event loop thread, but actual workload runs in `run_in_executor()`'s thread pool. Metrics capture the wrong thread → all async `os_metrics` show NaN for context switches. Documented, not fixed.

### `src/servers/flask_app.py`

Three modes in one file, controlled by environment variables:

| `EXECUTOR_TYPE` | `SCHEDULER_TYPE` | Behaviour |
|-----------------|-----------------|-----------|
| `baseline`      | ignored         | Workload runs synchronously in request thread. No dispatcher. |
| `thread`        | `fifo`/`priority` | ThreadPoolExecutor + Dispatcher |
| `process`       | `fifo`/`priority` | ProcessPoolExecutor + Dispatcher |

**How server waits for async executors:** Sets `job.on_complete` to a function that calls `event.set()`, then calls `event.wait(timeout=JOB_TIMEOUT)`. The event is a `threading.Event`.

**Routes:** `POST /run`, `GET /health`, `GET /stats`

**Run:**
```bash
EXECUTOR_TYPE=thread SCHEDULER_TYPE=priority python src/servers/flask_app.py
```

### `src/servers/fastapi_app.py`

Always uses AsyncExecutor. Scheduler controlled by `SCHEDULER_TYPE` env var.

**How server waits:** Creates `asyncio.Future`, sets `job.on_complete` to a callback that calls `loop.call_soon_threadsafe(future.set_result, completed_job)`. Then `await asyncio.wait_for(future, timeout=JOB_TIMEOUT)`. This is the correct pattern for bridging a non-async callback thread back into an asyncio coroutine.

**Lifespan:** Uses `@asynccontextmanager` lifespan pattern (FastAPI ≥0.93). Startup creates executor+dispatcher, shutdown calls `dispatcher.stop()` and `executor.shutdown()`.

**Run:**
```bash
uvicorn src.servers.fastapi_app:app --host 0.0.0.0 --port 8000
```

### `src/workloads/ml_simple.py`

Trains a `LinearRegression` model once at module load, then exposes `predict_batch(n_samples)` for inference-only workloads.

**Why predict-only:** Training during experiments would introduce non-deterministic CPU spikes unrelated to scheduling. The model is trained once, reused for all predictions.

**Lazy import in registry:** `from src.workloads.ml_simple import predict_batch` is inside the `ml_predict` branch of `run_workload()` so training only happens on first ML request per process.

### `src/utils/metrics.py`

`track_request()` is a context manager that takes psutil snapshots before and after a block and returns the delta dict:

```python
with track_request() as metrics:
    result = run_workload(...)
# metrics now has: duration_s, cpu_user_delta_s, cpu_system_delta_s,
#                  ctx_voluntary_delta, ctx_involuntary_delta,
#                  memory_mb, memory_delta_mb
```

## Known Limitations (documented, not fixed)

| Limitation | Detail |
|------------|--------|
| Async `os_metrics` NaN | `track_request()` runs in event loop thread but workload runs in `run_in_executor()` thread. psutil measures wrong thread. Context switches always NaN for async. |
| `execution_time` includes pool queue wait | `mark_started()` fires before executor submits to pool. If all workers are busy, `execution_time` includes wait inside the pool. Not purely workload time. |
| Low concurrency in experiments | 10 users produced sub-millisecond waiting times. Starvation not visible. Need 50+ users to show Priority starvation clearly. |
| No `perf` integration | Linux `perf` unavailable in WSL2. `psutil` used as portable alternative. Kernel-level tracing not possible. |
| `ml_predict` ctx switches NaN | psutil `num_ctx_switches()` occasionally fails for very short-lived workloads. |
| `experiment.yaml` empty | Config file not implemented. All configuration via env vars. |
| `docs/api.md`, `docs/experiments.md` empty | Not written. |

## Experiment Results Summary (2026-04-24)

- **1,150 jobs** across 7 configurations
- Process executor fastest for CPU (`cpu_fibonacci`: 0.132s) — GIL confirmed
- Async executor highest IO throughput (~243 jobs/60s vs ~137 thread/process)
- Priority scheduler increases IO waiting time 20–32% vs FIFO at 10 users
- Process executor highest context switches (mean 34.7/job) — IPC overhead
- `process_priority_cpu_fibonacci` anomaly: 222 ctx switches — priority starvation side effect
- Full analysis: `docs/results.md`

## Key Design Principles (viva-defensible)

1. **Scheduler is policy-only** — never executes jobs, only decides order
2. **Executor is mechanism-only** — never decides order, only runs jobs
3. **Dispatcher is the bridge** — makes scheduling delay measurable
4. **Workloads are pure** — no server/scheduler/metrics logic inside workloads
5. **Delta-based metrics** — measure what your code consumed, not process totals
6. **JSONL logging** — append-safe, streamable, no schema lock-in
